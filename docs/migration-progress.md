## Chunk 6 lifecycle contract

- `PUT /companies/{companyId}/members/{userId}/status` accepts `ACTIVE` (reactivate a removed membership) or `REMOVED`, with the latest membership revision.
- `POST /companies/{companyId}/members/{userId}/roles` assigns an explicit company-scoped `COMPANY_ADMIN`, `PROJECT_ADMIN`, or `MODERATOR` role. `DELETE .../roles/{role}?version=...` removes it. Global/platform roles are not assignable through these APIs.
- Removal revokes that company's role assignments, project memberships, active project assignments, moderator grants, and pending invitations to that member. Employment, historical work, global credentials, sessions, and other-company memberships remain intact. Reactivation restores membership only; old roles and project access stay revoked.
- Active project ownership/manager/approver duties must be reassigned, and pending time/expense submissions reviewed before removal. Changes reject stale revisions with HTTP 409.
- Last-admin checks count active memberships with company-scoped admin roles and available login accounts, excluding platform accounts. Shared company/account locks protect status changes, role removal, invitation acceptance, account locking/deactivation, and platform promotion.
- Project assignment and old invitations cannot implicitly reactivate removed memberships. Invitation acceptance uses a consistent account/company/invitation lock order. Project-administrator appointments require Company Admin permission.
- People search/status filtering is company-scoped. Project-only admins see only their assigned project teams, with restricted roster fields. Platform metadata administration does not grant People access.
- Password recovery uses the member's registered global login email, obtained on the server. It never accepts a destination email, password, or reset token from the People form.
- Ready work-record read paths also check active company membership, including owner reads, expense lists/details, approval periods, and PDF exports. Global login sessions survive company removal so other-company access remains usable.

## Chunk 7 settings contract

- `GET /companies/{companyId}/settings` returns a snapshot containing company ID, revision, update time, and an explicit map of company settings. `PUT .../settings/{key}` accepts only a value and expected revision. Active company-scoped Company Admin permission is required for reads and writes, with no legacy global Admin or platform bypass.
- Supported company keys are `company_name`, `vacation_days_per_year`, `sick_days_per_year`, `bereavement_days_per_year`, and `timesheet.reminders.enabled`. Unknown keys, blank/oversized display names, non-boolean reminder values, and leave values outside 0–366 or with more than two decimals are rejected.
- Display name is distinct from platform company metadata and workspace ID. Existing companies initialize from their own `companies.name`, never from the legacy global company name. Approved timesheet PDFs use the owning company's display name and omit the old fixed Maxwell branding. The shared application's existing product branding is unchanged.
- Existing company policy defaults are copied once from validated legacy settings. Future companies receive independent defaults of 15 vacation, 5 sick, 3 bereavement days, and reminders enabled. Company edits do not update global settings, other companies, annual published policies, or employee allowances. Chunk 8 must consume these defaults in its company policy publication workflow.
- Updates lock company administration and recheck permissions. Shared revisions reject concurrent stale edits with HTTP 409; required audit writes participate in the transaction. The frontend drops delayed responses after a switch/revocation and requires reload after a revision conflict.
- `GET /platform/settings` and `PUT /platform/settings/{key}` require current `canConfigurePlatform`. Only `platform.timesheet.reminders.enabled` is exposed, with a separate revision. SMTP/authentication secrets remain in deployment configuration and are never returned by either settings API.
- Reminder candidates must belong to an active company and project membership with current project submission roles, an active assignment/account, company reminders enabled, and platform delivery enabled. Removed members, project administrators, and platform accounts are excluded; delivery rechecks eligibility. Existing period cadence remains unchanged: closing-day reminders from 5 PM and late reminders after midnight, using the member's profile timezone.
- `/settings` and all old global key/bulk leave-default endpoints return HTTP 410. Do not restore the old global allowance application. Internal legacy leave services continue to read frozen compatibility defaults until Chunk 8.
- Frontend `/settings` and the Company settings menu are available only to Company Admins. `/platform-settings` is a separate platform-only route. Raw arbitrary settings and bulk leave application are absent from both screens.

Every operation resolves the current database platform assignment. Company/project roles and forged JWT/global role claims cannot authorize platform operations.
- Account responses expose only sign-in/identity administration metadata: name, login email, availability, scoped platform role, active membership count, revision, and setup-delivery status. Private profiles, medical/emergency fields, SSN, passwords, tokens, and company operational content are excluded. Global `/users/{id}` profile reads are self-only.

Platform appointments require an activated available account with no active company memberships. Availability changes preserve accounts/memberships/history while blocking company capabilities, work, confidential content, exports, notifications, reminders, and invitation acceptance. Resuming a company restores its retained current assignments; membership removal still revokes roles/grants separately.

The recipient still chooses their own password using the email-bound invitation. Delivery retries up to five attempts, shows safe status/error text, rechecks current invitation/company/account eligibility, and erases encrypted tokens after successful or cancelled delivery. Tokens/provider errors are never returned by management APIs.

Account activation links use URL fragments, with legacy query links still accepted by the activation page. Platform invitation lists contain only platform provisioning invitations, never company-issued employee/admin invitations.
